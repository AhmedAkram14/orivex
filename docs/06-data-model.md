3. Aggregate Design
   An aggregate is a transactional consistency boundary — everything inside it changes together, atomically; everything outside references it by ID only.
   Health Graph (per patient) Aggregate

Root: the patient's Health Graph itself (one per patient).
Child entities: individual nodes (conditions, symptoms, medications, lab results) and their edges.
Value objects: certainty level (suspected/confirmed/ruled-out, per Phase 2.5's Principle 7), clinical coding reference (ICD-11-aligned).
Invariants: a node cannot exist without at least one edge connecting it to a Visit or another node (nothing floats disconnected — this is what makes it a graph, not a list); a Resolved condition cannot transition back to Suspected (Phase 2.5's state machine) — reactivation creates a new linked node instead.
Business rules: only the treating doctor of the relevant Consultation Session may create or update nodes/edges tied to that encounter; patient self-logged data (e.g., home BP readings) attaches as a distinct node type that never alters a doctor-confirmed node's state directly (Phase 1.1's rule, enforced here as an aggregate invariant).
Transactional boundary: a single consultation's clinical documentation (note + diagnosis + prescription + lab request + graph update) should commit as one transaction — either the whole clinical record of the encounter is saved, or none of it is; a partial save (e.g., a prescription exists but the diagnosis node it depends on doesn't) is an invalid state the aggregate must prevent structurally.

Health Journey Aggregate

Root: the Journey itself.
Child entities: stage history (Diagnosis → Follow-up → Recovered, etc.), linked graph node references.
Value objects: current stage, "who last updated this and when."
Invariants: only a doctor can advance clinical stage (Phase 1.1's rule); a Journey always has exactly one root condition node, with any part_of sub-conditions as children (Phase 2.5's ADR-003 resolution).
Transactional boundary: a Journey update commits alongside the triggering Clinical Note/Diagnosis (same transaction as the Health Graph update above, in practice — Journey and Graph updates for one encounter are one atomic unit, not two separate writes that could drift out of sync).

Consultation Session Aggregate

Root: the session itself.
Child entities: session state transitions, connection-quality logs, Emergency Escalation flag if triggered.
Value objects: session duration, completion status.
Invariants: cannot transition to Closed without either a completion reason or an explicit interruption reason (Phase 2.5's state machine) — no session silently disappears without a terminal state explaining why.
Business rules: billing trigger only fires on a valid Completed transition, never on Interrupted without an explicit no-fault resolution rule applied (Phase 2 edge case 4).
Transactional boundary: session state transitions are their own aggregate, separate from the Clinical content produced during the session — this deliberately mirrors Phase 3's Consultation-vs-Clinical domain split at the aggregate level too.

Prescription Aggregate

Root: the Prescription.
Child entities: line items (medications, dosage, instructions).
Value objects: digital signature, issued timestamp.
Invariants: immutable once signed (Phase 1.2's medical record integrity principle) — any correction creates a new Prescription that supersedes it, never an edit of the original.
Business rules: cannot be created without a linked, completed Consultation Session and a linked diagnosis/condition node (no orphan prescriptions).

Consent Record Aggregate

Root: the Consent Record (one per patient-doctor-scope combination, versioned).
Child entities: version history entries.
Value objects: scope (which data categories), grant/revoke timestamp.
Invariants: never physically deleted, only appended with a new version reflecting revocation (Phase 2.5's state machine — consent state is fully versioned).
Business rules: a revocation is forward-only (doesn't retroactively alter access already exercised during an active session, per Phase 2's edge case 46).

AI Suggestion Record Aggregate

Root: the Suggestion Record.
Child entities: none typically (a fairly flat entity).
Value objects: the exact input context snapshot, the generated output, the doctor's action (approved/edited/rejected) and justification if overridden.
Invariants: immutable once the doctor has acted on it — this is an audit artifact, not a working document (Phase 4's liability-reconstruction requirement made concrete).
Business rules: never has write access to Health Graph directly; its only path into clinical truth is via a separate, doctor-authored Clinical Note/Prescription/Graph update that references the suggestion it was based on.

Verification Case Aggregate

Root: the Verification Case.
Child entities: submitted documents (references to Media Assets), review decisions.
Value objects: decision reason, reviewer identity.
Invariants: a Doctor Profile cannot be publicly visible/bookable while its associated Verification Case is not in an Approved state.

4. Entity Relationships (Conceptual)

Account ↔ Patient Profile / Doctor Profile: one-to-one — every Patient/Doctor Profile has exactly one owning Account, but an Account's role determines which profile type it has, not both simultaneously in V1 (a patient-who-is-also-a-doctor would need two accounts in the current model — worth flagging as a real, if rare, future edge case).
Patient ↔ Health Graph: one-to-one — each patient has exactly one Health Graph (their entire clinical history), which internally contains many nodes.
Health Graph ↔ Health Journey: one-to-many — one Graph can have many Journeys, each Journey referencing a subset of the Graph's nodes; a node can, in principle, belong to more than one Journey (many-to-many at the node level) if a symptom is relevant to two concurrently-tracked conditions — this needs to be modeled deliberately, not assumed away.
Doctor ↔ Consultation Session: one-to-many.
Patient ↔ Consultation Session: one-to-many.
Consultation Session ↔ Clinical Note: one-to-one typically (one primary note per session), though addenda (Principle 4, Phase 2.5) create additional linked note entries — effectively one-to-many when corrections are included.
Clinical Note ↔ Health Graph Node(s): many-to-many — a single note might update multiple nodes (a new diagnosis plus a medication change), and a single node accumulates references from many notes over time (composition/aggregation, not strict ownership — the Node is owned by the Graph aggregate, not by any individual Note).
Prescription ↔ Health Graph Node (diagnosis): many-to-one — many prescriptions can trace back to one condition over time (e.g., repeated hypertension prescriptions).
Doctor ↔ Knowledge Article: one-to-many (composition — an article's lifecycle is bound to its authoring doctor's standing, per Phase 2 edge case 71's nuance about suspended-doctor content).
Patient ↔ Consent Record: one-to-many (one per doctor/scope combination) — this is a genuinely important many-sided relationship (patient × doctor × category), not a simple pair.
Consultation Session ↔ Payment Transaction: one-to-one (typically) for paid consultations; zero for free consultations (a real, valid absence, not a null placeholder — free consultations should not have a "zero-dollar" Payment Transaction record at all, consistent with Phase 1's business rule that free flows structurally differ from paid ones).
AI Suggestion Record ↔ Clinical Note/Prescription: reference only (lifecycle dependency, not ownership) — a Clinical Note may reference the AI Suggestion it was derived from, but deleting/superseding a Note never deletes the underlying Suggestion Record, which persists independently as an audit artifact.
Media Asset ↔ (Clinical Note | Consultation Session | Patient Profile): reference-only, many-to-one from the Asset's perspective (one asset belongs to exactly one owning context) but the owning domain's entity can reference many assets.

5. Health Graph Modeling
   Representation: Nodes typed by category (Condition, Symptom, Medication, Lab Result, Radiology Result, Visit, Doctor-as-participant), edges typed by relationship (diagnosed_during, treated_with, confirmed_by, caused_by/contraindicated_by, related_to, part_of) — this is the same model established conceptually in Phase 2.5, now given data-ownership rigor: the Graph is Clinical Domain's aggregate, and every node/edge write is transactionally scoped to the Consultation Session that produced it (Section 3's invariant), which is what prevents the Graph from becoming an inconsistent, un-auditable mess as it grows.
   How Journeys are built from the Graph: A Journey is not a separately-stored copy of clinical data — it's a named traversal definition (root node + part_of children + the linear stage-sequence view over diagnosed_during/treated_with edges touching that subtree). This is the concrete resolution promised in Phase 2.5: Journeys don't duplicate Graph data, they curate a view of it. This matters enormously for data integrity — if Journeys stored their own copy of clinical facts, a correction to the Graph could silently leave a Journey's view stale; because Journeys are traversals, not copies, they're always consistent with the underlying Graph by construction.
   How AI uses the graph: The AI Layer (Phase 4) receives a bounded subgraph query result — the current condition in focus plus its directly connected nodes within a defined traversal radius — never the full graph indiscriminately (Phase 2.5/4's scoping rule, now expressed as a literal query-boundary constraint on the data layer itself, not just an application-level convention).
   How doctors navigate it: Primarily through the Journey view (a linear narrative), with the full Graph exposed only as an optional "explore connections" mode for complex cases (Phase 2.5) — this is a data-model note worth restating here: the Graph's query interface needs to support both a fast, narrow "give me this Journey's traversal" query and a slower, broader "show me everything connected to X" query, and these are genuinely different access patterns the storage technology (Phase 4, Section 9) needs to support well.
   How future wearable data fits: Each node carries a source attribute (clinical/doctor-authored vs. patient-self-reported vs. device-generated, per Phase 2 edge case 57's anticipation) — a wearable data point becomes a new node with source: device, connected via related_to or confirmed_by edges to relevant conditions, without requiring any structural change to the Graph model itself. This is a genuine "attaches cleanly" case, unlike some of the harder future-expansion items flagged in earlier phases.

6. State Models
   Building directly on Phase 2.5's Section 9 — restating here with the data-ownership lens (which aggregate governs each transition):

Appointment: Requested → Confirmed → (Rescheduled | Cancelled | No-Show | Completed). Governed entirely within the Consultation Session aggregate; no other domain can write this state directly.
Consultation: Scheduled → Waiting Room → In Progress → (Completed | Interrupted) → Closed, with Emergency Escalation as an exceptional branch. Same aggregate as above.
Prescription: Draft → Doctor-Edited → Signed → (Active | Expired | Superseded). Once Signed, the aggregate becomes immutable (Section 3) — any further state is a new Prescription aggregate instance referencing the prior one, not a mutation.
Consent: Not Granted → Granted (scoped) → Revoked, fully versioned, governed by the Consent Record aggregate, never touched by any other domain's write path.
Doctor Verification: Submitted → Under Review → (Approved | Rejected | More Info Needed) → Re-Verification Due → (Approved | Suspended). Governed by the Verification Case aggregate.
Knowledge Article: Draft → (Pre-Review | Published) → (Flagged → Under Review → Reinstated | Removed) → Needs Update (non-blocking).
Payment: Initiated → (Succeeded | Failed) → (Settled | Refunded | Disputed). Governed by Payment Transaction aggregate, with idempotency guarantees (Section 7) preventing duplicate transitions from retried requests.
Health Journey: Diagnosis → Follow-up → Monitoring → (Resolved | Ongoing/Chronic) , with Referred Out as a terminal-ish honest state (Phase 2.5's Section 12 addition) representing "requires care outside this platform" rather than forcing an artificial on-platform resolution.

Cross-cutting rule: no state model here permits a "backward" transition that would imply erasing what happened — every apparent reversal (a resolved condition recurring, a rejected verification later approved) creates a new forward-only entry referencing the prior state, never a literal rollback. This is Principle 4 (Phase 2.5) enforced structurally across every state model in the system, not just the clinical ones.

7. Data Consistency Strategy
   Strong consistency required for:

Within a single aggregate (Section 3's transactional boundaries) — e.g., a Consultation Session's clinical documentation (note + diagnosis + prescription + graph update) must commit atomically as one unit; a partially-saved encounter is a patient-safety hazard, not just a technical inconvenience.
Payment Transaction state transitions (Section 6) — a double-charge or a charge-without-booking (Phase 2 edge case 16) is unacceptable, requiring strict transactional guarantees plus idempotency keys.
Consent state at the moment of data access — a doctor's request to view Patient data must check current consent state synchronously and strongly, not against a potentially-stale eventually-consistent cache (a stale "yes" here is a privacy violation, not a minor lag).

Eventual consistency acceptable for:

Search indexes (Phase 4, Section 10) — a few seconds' lag before a new Knowledge Article appears in search is fine.
Analytics aggregates — inherently derived and always slightly behind real-time by design.
Notification delivery — asynchronous by nature.
Patient Domain's display of Clinical Domain content (the Health Passport reading Health Graph updates) — a brief lag between a doctor signing a prescription and the patient's Passport view refreshing is acceptable, since the authoritative write already succeeded strongly within Clinical Domain itself.

Cross-domain consistency: achieved via the event-driven model (Phase 3/4) with eventual consistency as the norm between domains — strong consistency is reserved for within a single domain's aggregate boundary, never promised across domain boundaries. This is a deliberate, named trade-off: cross-domain strong consistency (distributed transactions across Clinical, Consultation, and Payments simultaneously) would reintroduce the tight coupling DDD is meant to avoid, and isn't actually needed if each domain's own aggregate boundary is drawn correctly (per Section 3).
Concurrency handling: optimistic locking (version-checked writes) for aggregates with plausible concurrent-edit scenarios — e.g., two admins acting on the same Moderation Case (Phase 2 edge case 78), or a doctor editing Availability while a patient is mid-booking the same slot (Phase 2 edge case 17's race condition) — the latter specifically warranting a short pessimistic lock/reservation (Section 4's slot-hold pattern) rather than pure optimistic retry, since the user-facing cost of a failed booking attempt is higher than the cost of a brief hold.
Conflict resolution: Health Graph conflicts (two doctors documenting differing views on the same condition, Phase 2 edge case 48) are never auto-resolved — both entries persist with authorship/timestamp, consistent with Principle 4; this is a deliberate refusal to apply automatic conflict resolution to clinical content, where "let the computer decide who's right" is actively the wrong answer.
Idempotency: required at every write boundary that could be retried by a client or a queue consumer (booking confirmation, payment capture, AI suggestion generation) — idempotency keys derived from the originating request, not from timing, since network retries are a certainty at any real scale.

11. Audit Strategy
    What must be audited: every access to Sensitive Medical Data (PHI) — who, when, why (Phase 1.2's Trust Layer); every state transition on Consent, Verification, Prescription, and Consultation aggregates; every AI Suggestion generated and the action taken on it; every Admin action on any entity.
    What must never be editable: signed Prescriptions, closed Consultation Session clinical content, Consent version history, Audit Log entries themselves, AI Suggestion Records once acted upon. All of these are append-only by design (Section 9) — this isn't a permissions setting that could be misconfigured, it's a structural property of these aggregates.
    Version history: required wherever "evolve, never rewrite" applies (Principle 4) — Health Graph, Journeys, Prescriptions (via superseding), Consent, Doctor credentials (each verification-triggering edit).
    Medical record immutability: the single hardest-line rule in this entire document — a Clinical Note, once tied to a Closed Consultation Session, is never edited; any correction is a new, clearly-linked addendum entry, timestamped and attributed, with both the original and the correction visible to any future reader (never a silent replacement).
    AI suggestion history: every suggestion's exact input context, output, and doctor disposition retained permanently (Section 9) — this is the concrete data-layer requirement satisfying Phase 4's liability-reconstruction need, and it should be understood as one of the largest-volume, longest-retained data categories in the entire system, not a minor logging table.
    Doctor approval history: captured as part of the AI Suggestion Record itself (the "doctor's action" field) rather than as a separate parallel log — keeping this co-located with the suggestion it responds to avoids the two records ever drifting out of sync.

12. Future Evolution

Multi-country: the Consent Record and Verification Case aggregates are the two most likely to need country-specific extension (different legal consent language, different licensing-body integration per Phase 4's honest ADR-004 risk) — the data model should treat "which country's rules apply" as an explicit attribute on these aggregates from V1, even though only Egypt's rule-set is implemented, so a second country is a new rule-set, not a schema change.
Multi-language: content entities (Knowledge Articles, Doctor Portfolio bios) should model language as an explicit attribute per content instance (supporting multiple language versions of the same underlying article) rather than assuming a single global language field — cheap to model now, expensive to retrofit.
Insurance: Payment Transaction aggregate is the natural attachment point for future claims data — a claims sub-entity referencing existing transactions, not a restructuring.
Hospitals/Laboratories/Pharmacies: attach via new entities referencing existing Clinical Domain artifacts (Lab Request, Prescription) as already anticipated in Phase 3/4's Future Integrations boundary — no changes to Clinical Domain's core aggregates needed.
Wearables: attaches as a new source: device node type within the existing Health Graph model (Section 5) — genuinely the cleanest future-attachment case in this entire document.
Government integrations: Verification Case's external-reference field (Syndicate license number) is the existing attachment point; a formal government API integration (Phase 1's UHIS research) would populate/validate this field automatically rather than requiring new structural concepts.
Research: consumes only the Analytics Domain's de-identified aggregates (Section 8) — this boundary must be treated as hard and non-negotiable; Research access should never have a path to identified Clinical Domain data, by construction, not by policy alone.

14. Final Database Architecture Review
    Weak aggregates: The Notification and Settings aggregates are appropriately thin (correctly so — over-modeling these would be a waste of design effort relative to their actual complexity).
    Overloaded entities, honestly: The Health Graph aggregate (per patient) is, by design, the heaviest and most complex in the entire system — this has been flagged in every phase since Phase 2.5 and remains true here at the data-modeling level specifically; it will require the most careful internal partitioning (per-condition sub-aggregates conceptually, even if the "per patient" Graph is the outer consistency boundary) when Physical Database Design begins.
    Poor ownership, resolved but worth restating: The Patient/Clinical split (Section 1) is the one ownership boundary most likely to be quietly violated in practice if engineers aren't careful — a tempting shortcut would be to let Patient Domain cache a copy of "current medications" for fast Health Passport display, which would violate single-ownership. The correct pattern is Patient Domain always querying Clinical Domain's current data (accepting the eventual-consistency lag, Section 7) rather than maintaining a shadow copy — this needs to be an explicit, enforced convention going into Physical Database Design, not left to individual engineer judgment.
    Missing concepts: A legal hold mechanism (mentioned in Section 9's table cells) is real but hasn't been given its own first-class treatment as a cross-cutting concept — recommend it become an explicit attribute/mechanism applicable to any aggregate, not something implied only for clinical records.
    Future bottlenecks: The AI Suggestion Record's volume (Section 13) is a genuine, foreseeable scale problem worth budgeting for now rather than discovering as a cost surprise later.
    Technical debt, consciously accepted: The account-deletion-vs-retention question (Section 13) is the single most important open item carried into Physical Database Design — it directly affects how several entities' lifecycle is actually implemented, and proceeding without a legal answer risks building the wrong mechanism entirely.

Strong recommendation: Settle the Health Graph storage technology direction (graph-native vs. relational-with-graph-modeling) before ERD, since it materially changes how nodes/edges would even be represented in a physical schema — this doesn't need to be a final vendor choice yet, but the category of technology should be decided going in.
With those two resolved, this conceptual model is thorough, internally consistent, and rigorous enough to move confidently into Physical Database Design.
