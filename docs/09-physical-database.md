Phase 8 — Physical Database Design (Enterprise ERD)
First implementation-oriented document in this series — I'll go concrete: real column-level detail for the highest-risk tables (Health Graph, Consent, AI Suggestion, Prescription), and consistent, clearly-stated patterns for the rest, rather than mechanically exhausting every column of ~40 tables.

9. Audit Strategy (Table Design)
   audit.audit_log_entries columns: audit_entry_id (PK), account_id (nullable — null for system-initiated actions), action_type (ENUM: read/create/update/state_transition/etc.), entity_type, entity_id (polymorphic reference to the audited row), before_state (JSONB, nullable — populated for updates/transitions), after_state (JSONB), reason (TEXT, required for admin overrides and AI-suggestion rejections per Section 3's justification requirement), source (ENUM: web/mobile/api/system-job), ip_address (INET), session_id (FK, nullable), created_at (TIMESTAMPTZ, no default other than now(), and critically no updated_at column exists on this table at all — the strongest possible physical signal that this table is genuinely append-only).
   JSONB for before/after state is the right call here specifically (Section 13) — the shape of "what changed" varies enormously by entity type, and forcing this into a fully normalized structure would create an enormous number of narrow, rarely-useful audit-detail tables for little real benefit.

12. Performance Review
    Large tables (by projected row count): health_graph_nodes, observations, ai_suggestions, audit_log_entries, notifications — in roughly that order at scale (Phase 4's scaling tiers). These are exactly the tables flagged for partitioning (Section 7).
    Hot tables (high read/write frequency relative to size): consultation_sessions and availability_windows during peak booking hours — the Phase 2 edge case 17 race condition (double-booking) means this table needs careful concurrency handling (a short-lived reservation row or advisory lock pattern during checkout, not just an optimistic-locking retry, given the user-facing cost of a failed booking).
    Expensive queries to watch: "Give me this patient's full Health Journey with all linked nodes and their edges" is a recursive, potentially multi-hop query — this is the query Section 13's recursive CTE approach exists to serve, and it's worth flagging now that this specific query pattern deserves dedicated query-plan review once real data volume exists, since a naive recursive query over a deeply-connected graph could degrade badly.
    Potential bottlenecks: ai_suggestions growing unboundedly (Section 7) is a storage-cost bottleneck more than a query-performance one, provided partitioning and cold-tiering are applied early; health_graph_nodes composite lookups (Section 6) are the query-performance bottleneck to watch most closely, since they sit directly in the critical path of every consultation (Patient 360 Tier 1 load, Phase 2.5).
    Future optimizations: materialized views for Doctor/Platform Analytics (Section 13); potential read replicas for Discovery/Search-heavy read traffic once scale demands it (Phase 4's 100k-user tier); revisit whether health_graph_nodes/edges eventually warrant a dedicated graph-query extension or even the previously-deferred graph-native technology (Phase 5/6 flagged this as an open question resolved for now by the ADR assumption of relational recursive modeling — worth revisiting if query performance at real scale proves the recursive-CTE approach insufficient).

13. PostgreSQL Best Practices

UUID strategy: UUIDs (v4 or v7 if available for better index locality) as primary keys across the board — chosen over serial integers specifically because this system anticipates eventual multi-region deployment (Phase 4) where centrally-coordinated integer sequences would be awkward; UUIDs generate independently per region without collision risk.
Timestamp strategy: TIMESTAMPTZ exclusively, never naive TIMESTAMP — server-authoritative, UTC-stored, converted to local/display timezone only at the presentation layer (Phase 2's timezone-handling rule, made physically concrete).
JSONB usage: reserved for genuinely variable-shape, low-transactional-integrity-need data — audit_log_entries.before_state/after_state, ai_suggestions.safety_flags. Deliberately not used for anything that should be relationally queryable/constrained (e.g., Prescription line items are real rows, not a JSONB array, precisely because they need FK integrity to the Drug Catalog and immutability guarantees a JSONB blob wouldn't structurally enforce).
ENUM usage: for genuinely closed, rarely-changing vocabularies defined by the business itself (certainty_level, consultation state, doctor_decision). Not used for anything that might need runtime extension by non-engineering staff (Specialties, ICD-11 codes, Drug Catalog) — those live in reference schema tables instead, consistent with Phase 6's Configuration/Reference Data domain design, since adding a new specialty shouldn't require an ALTER TYPE migration.
Partial indexes: used extensively for status-filtered hot paths (WHERE status = 'pending' on verification/moderation queues, Section 6) — much smaller and faster than full-table indexes for these overwhelmingly common filtered queries.
GIN indexes: for the Full Text Search columns (knowledge_articles, doctor_profiles per the V1 technology assumption) via tsvector generated columns.
Generated columns: a search_vector generated column (GENERATED ALWAYS AS (to_tsvector(...)) STORED) on knowledge_articles and doctor_profiles, keeping the FTS index automatically in sync without application-layer maintenance.
Constraints: CHECK constraints for enum-like validation and value ranges (confidence scores, version numbers), enforced at the database level as a genuine safety net beyond application validation — given healthcare stakes, defense in depth here is worth the minor rigidity cost.
Materialized views (future): for Analytics Domain's derived aggregates (Doctor performance summaries, Platform liquidity metrics) — refreshed on a schedule, never queried live against operational clinical/consultation tables directly, consistent with Phase 4/5's "Analytics never degrades operational performance" rule.
Recursive CTEs: the mechanism by which the Health Graph's node/edge traversal (Journey construction, "explore connections" views, Phase 2.5/5) is queried under the ADR's relational-modeling assumption — this is the direct physical implementation of the graph-without-a-graph-database approach, and its performance characteristics at scale are the one thing worth monitoring most closely post-launch (Section 12).

14. Final ERD Review
    Normalization issues: doctor_portfolio_publications/doctor_portfolio_awards being split into two tables (per Phase 6's readiness recommendation) is the right call and has been carried through here — worth confirming this resolved cleanly rather than reintroducing a single generic "portfolio item" table under time pressure during actual implementation.
    Over-normalization risk: journey_node_links and note_node_links as separate junction tables (rather than one generic "clinical_entity_links" polymorphic table) is intentional, not an oversight — a generic polymorphic junction table would save two table definitions but lose real FK integrity and make query planning worse; this is a case where slightly more tables is the more correct choice, not premature normalization.
    Missing tables, found at this stage: reference.consent_text_versions (referenced in Section 3's consent_records.legal_basis_reference_id) wasn't explicitly listed in Section 2's reference schema table list — adding it now: this table stores the actual versioned consent-language text a patient agreed to, and is genuinely necessary for Phase 2 edge case 100's regulatory re-consent scenario to be implementable at all.
    Missing relationships: referrals (Section 2) currently only links to journey_id and doctor/specialty references — it's worth adding an optional outcome_lab_result_id/outcome_note_id nullable reference for the (uncommon but valuable) case where the referred-out care eventually produces a result the patient/doctor manually links back in, closing the loop honestly rather than leaving referrals as permanent dead ends in the data model.
    Future scalability risks: the recursive-CTE approach to Health Graph traversal (Section 13) is the single biggest open technical risk carried through from Phase 5/6 — this document proceeds on the given ADR assumption, but it's worth stating plainly one more time that this should be load-tested against realistic graph depth/breadth before being trusted at the 1M+ user scale tier (Phase 4, Section 13), not assumed to hold by extrapolation.
    Healthcare compliance concerns: the account-deletion-vs-retention legal question, unresolved since Phase 2.5, has been given a provisional physical mechanism here (anonymize PII, retain RESTRICT-protected clinical history) — this is a reasonable default implementation, but it is still explicitly provisional pending actual legal confirmation, and should be flagged as such to whoever signs off on compliance before this ships.
    Technical debt, consciously accepted: Mental Health-specific access rules being enforced at the application layer rather than expressible as a pure database constraint (Section 11) is a known, accepted limitation of the relational-modeling approach — worth documenting explicitly as a place where application-layer discipline is doing safety-critical work that the schema alone cannot guarantee.
