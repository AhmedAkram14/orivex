3. Architectural Style — The Central Decision
   Evaluation:
   StyleFit for this projectPure MicroservicesWrong choice for V1. A team building this from scratch faces enormous premature operational overhead (service mesh, distributed tracing, inter-service auth, data consistency across service boundaries) before there's any real scale justifying it. Microservices solve organizational scaling (many independent teams) and load-scaling problems this project doesn't have yet.Pure Layered Architecture (traditional 3-tier)Too weak a boundary discipline for a domain this complex — it tends to let business logic leak into whichever layer is most convenient, which is exactly the "Clinical Domain overloaded" risk Phase 3 already flagged as a concern to manage carefully.Modular MonolithRecommended for V1. Preserves Phase 3's bounded contexts as enforced internal module boundaries (separate packages/namespaces, explicit internal APIs between them, no reaching into another domain's internals) while deploying as one unit — dramatically simpler operations, transactions, and debugging for a team at this stage, without sacrificing the domain discipline that makes a future split possible.Event-DrivenAdopted within the modular monolith for cross-domain communication (Section 5), not as a replacement for it — events and modularity aren't alternatives, they're complementary.Hexagonal/Clean ArchitectureAdopted within each domain module — each bounded context internally follows ports-and-adapters (domain logic isolated from persistence/external-service details) so that, e.g., swapping the video provider (Section 11) or the AI model provider (Section 7) doesn't ripple into domain logic. This is the mechanism that makes "future split into microservices" realistic later without a rewrite.Vertical Slice ArchitectureA reasonable alternative organizing principle within a domain module (organizing by feature/use-case rather than by technical layer) — worth adopting as an internal convention for the more complex domains (Clinical, Consultation) rather than a project-wide mandate.CQRSSelectively applied, not project-wide — most valuable for Clinical Domain (where read patterns like "give me the Patient 360 view" are structurally very different from write patterns like "record a diagnosis") and for Analytics (which is inherently read-model-only already). Applying CQRS everywhere would be overengineering for modules like Settings or Notifications where read/write patterns aren't meaningfully divergent.
   Recommendation, stated plainly: A Modular Monolith, internally structured with Hexagonal boundaries per domain and Domain Events for cross-domain communication, with CQRS applied selectively to Clinical Domain and Analytics. This is not a "startup shortcut we'll regret" — it is the correct choice at this stage for a team that needs velocity and operational simplicity while preserving a genuine path to splitting out the highest-scale domains later.
   How it evolves over time: Because domain boundaries are enforced as real module boundaries (not just folder conventions), the domains most likely to need independent scaling first — Consultation/Realtime (video load scales differently from everything else) and AI Copilot (compute-heavy, benefits from independent scaling and possibly different infrastructure/GPU needs) — can be extracted into standalone services first, while the rest of the system remains a monolith. This is a realistic, incremental "strangler" evolution path, not a hypothetical one — worth stating that these two are the most likely first candidates for extraction, specifically because Section 13's scaling analysis will show they're the components with fundamentally different load profiles from the rest.

   PatternUsed forWhyDirect (in-process) callsSame-domain logic, and synchronous cross-domain reads where the caller needs an immediate answer (e.g., Consultation Domain checking Doctor availability at booking time)Lowest latency, simplest to reason about; appropriate because these are genuinely synchronous decisions, not eventual-consistency-tolerant onesDomain Events (internal event bus)Cross-domain reactions where the producer doesn't need to know or care who consumes (e.g., HealthGraphUpdated → Patient Domain refresh, AI Copilot context refresh)Decouples domains per DDD principle; this is the backbone of Phase 3's event mapQueues (async job processing)Non-urgent, potentially slow work — AI suggestion generation, document OCR processing, data export generation, notification batch digest compilationProtects user-facing request latency from slow background work; also gives natural retry/backoff semantics for flaky external dependencies (Section 11)Pub/SubFan-out scenarios — one event needs to reach many independent consumers (e.g., DoctorSuspended needs to reach Consultation, Knowledge, and Notifications simultaneously)The natural pattern once you have more than one or two consumers per event; the internal event bus is effectively a pub/sub mechanismScheduled/Cron JobsPeriodic checks — license re-verification triggers, follow-up reminder generation, content-freshness prompts (Phase 2 edge case 75), stale-data cleanupTime-based rather than event-based triggers, a genuinely different categoryRealtime/WebSocketsVideo session signaling, live AI suggestion delivery to the Workspace, live presence/availability updates, in-call chatThe one place true persistent bidirectional connections are actually needed — everything else above can be request/response or async

   Structure common to all four domains (Clinical/Doctor/Patient/Operational Intelligence):
   Context Gathering → Safety/Scope Layer → Model Routing → Generation → Approval Gate → Audit Log
   DomainInputsOutputsContext scopeClinical IntelligenceLive transcript, scoped Health Graph subgraph (Phase 2.5), current working context (active Journey)SOAP drafts, prescription drafts, interaction/allergy flags, suggested questionsTightly scoped to the current consultation + directly connected graph nodes — never the patient's unrelated full historyDoctor IntelligenceDoctor's own practice data (Portfolio, Analytics, patient search trends)Growth suggestions, content topic ideas, scheduling insightsScoped to one doctor's own data onlyPatient IntelligencePatient's own Health Passport/Journey dataTimeline summaries, appointment prep, health insightsScoped to one patient's own data onlyOperational IntelligenceAggregated, de-identified platform data (bookings, cancellations, liquidity signals)No-show risk scores, fraud flags, liquidity forecastsCross-patient/doctor, but strictly de-identified/aggregated — never identified individual clinical content
   Approval Workflow (Clinical Intelligence specifically — the highest-stakes path): every generation produces a draft object with a stored snapshot of its exact input context; the doctor's accept/edit/reject action is itself logged against that exact draft (satisfying Phase 1.2's liability-reconstruction requirement); only the approved, possibly-edited content is written to Clinical Domain — the AI Layer itself never has write credentials to Clinical Domain's data store, enforced at the infrastructure/permissions level, not just in application code.
   Model Routing: Not all AI tasks warrant the same model — deterministic tasks (drug interaction/allergy checking, per Phase 2.5's hard rule) route to a rules/database lookup engine, not a generative model at all; language-generation tasks (drafting, summarizing, transcription) route to an appropriate LLM; classification tasks (no-show risk, fraud flagging) route to a lighter-weight predictive model. This routing layer is the concrete architectural enforcement of the deterministic-vs-generative distinction Phase 2.5 insisted on — it must be a hard routing rule, not a prompting convention that could be bypassed under engineering time pressure.
   Prompt Layer: Templated, versioned prompts per suggestion type (not free-form ad hoc prompting scattered through the codebase) — this matters because prompt changes affect clinical-suggestion behavior, and need the same change-review rigor as any other clinically-relevant code change.
   Safety Layer: Sits between context gathering and generation — checks for scope violations (e.g., is this request trying to get a diagnosis-as-fact rather than a draft-with-caveats), confidence thresholds (below-threshold outputs are suppressed per Phase 2.5's "AI remains silent" principle), and content policy (nothing that reads as autonomous clinical authority).
   Human Approval: Universal and non-bypassable for Clinical Intelligence outputs; Doctor/Patient Intelligence outputs are informational and don't require the same gate (per Phase 1.2's distinction), though they should still be clearly labeled as AI-generated.
   Auditability: Every AI generation, its exact inputs, its exact output, and the human action taken on it is retained — this is a genuinely significant storage/logging requirement (Section 9), not a minor logging afterthought.
   Future evolution: As model providers and capabilities evolve, the Model Routing layer is the isolation point that absorbs that change — swapping or adding model providers should never require touching Clinical Domain code, only the AI Layer's internal routing configuration (a direct application of the Hexagonal boundary principle from Section 3).

10. Search Architecture (Engineering Lens)
    Building directly on Phase 3's Section 8 — the engineering addition is the indexing/consistency model:

Indexing strategy, conceptually: each domain emits events on data change (DoctorProfileUpdated, KnowledgePublished, HealthGraphUpdated); a dedicated indexing consumer per domain projects those events into that domain's search index asynchronously — meaning search results are eventually consistent, not transactionally guaranteed in real-time. This is an acceptable, standard trade-off for search (a few seconds of lag before a newly published article appears in search is fine); it would not be acceptable for, say, an availability slot's booking status, which needs synchronous consistency (handled by Section 5's direct-call pattern instead, not through search).
Semantic/AI-assisted search: layered as a ranking/query-interpretation step in front of the structured indexes (Phase 3), never replacing structured filtering entirely — a deterministic fallback (plain keyword/filter search) must always exist alongside the AI-assisted layer, particularly important for Clinical Search (Phase 3) where a doctor needs reliable, literal search over their own patient panel, not just semantic best-guessing.
Admin Search: the justification-logging requirement (Phase 3) is enforced at the search-query layer itself — every admin search against patient-scoped data triggers an audit log entry as an inherent part of executing the query, not a separate manual logging step an admin could skip.

    EnvironmentPurposeDevelopmentLocal/ephemeral, mirrors production configuration via Infrastructure as Code, seeded with synthetic (never real patient) dataTesting (CI)Automated test execution on every change — unit, integration, and domain-boundary-contract tests specifically (verifying, e.g., that Clinical Domain's public interface hasn't silently changed in a breaking way)StagingProduction-like environment for pre-release validation, including realistic (still synthetic) load and security scanningProduction (Egypt region, V1)The live system, region-locked for data residency (Section 8)Future Multi-regionAdditional regions added as new countries launch (Section 13/14), each with its own data-resident storage, sharing the application layer's codebase but not its data stores across regions — this is the concrete mechanism by which "globally scalable, multi-region ready" (the original constraint from Phase 1) and "Egyptian data stays in Egypt" coexist without contradiction
    Supporting practices:

Containerization: the modular monolith deploys as a set of containerized services (even if logically one application, physically deployable/scalable in defined units — e.g., the Realtime/video component may warrant its own container scaling profile even while sharing a codebase with the rest, anticipating Section 3's future extraction).
CI/CD: automated pipeline from commit → test → staging → production, with domain-boundary contract tests as a hard gate, not just unit tests.
Infrastructure as Code: all environments defined declaratively, so region replication (multi-region future) is a repeatable process, not manual reconstruction.
Secrets Management: centralized vault, environment-specific scoping.
Monitoring, Logging, Alerting: observability-first (Section 1) — structured logs, distributed tracing across domain boundaries even within the monolith (so a slow request can be traced through Consultation → Clinical → AI Layer calls), and alerting tuned to the clinically-critical paths specifically (video/booking uptime alerts are higher priority than, say, Knowledge Center latency).
Health Checks & Autoscaling: standard practice for the stateless portions of the system; the Realtime/video layer needs its own specific scaling logic given its statefulness (Section 6).
Blue/Green Deployment: preferred over risky in-place updates, particularly important for a system where downtime has real clinical consequence (Phase 1's NFR).
Disaster Recovery: as defined in Section 8, with the core clinical/booking/video path as the explicit top DR priority.

15. Architecture Decision Records (Key ADRs)
    ADR-001: Modular Monolith over Microservices for V1

Alternatives: Pure microservices from day one; pure layered monolith with no domain discipline.
Pros: Lower operational overhead, simpler transactions/debugging, faster initial velocity, preserves a genuine extraction path later.
Cons: Requires real discipline to avoid boundary erosion; won't automatically scale each domain independently without later extraction work.
Reasoning: This project doesn't yet have the organizational scale (many independent teams) or load-scale that justifies microservices' overhead; the enforced domain boundaries capture most of microservices' long-term benefit without the near-term cost.
Long-term impact: Makes Section 13's scaling story realistic rather than requiring a rewrite at scale.

ADR-002: Deterministic Lookup (Not Generative AI) for Drug Interaction/Allergy Checking

Alternatives: Use the same LLM used for drafting/summarization for interaction checking too.
Pros of chosen approach: Predictable, auditable, verifiable against a maintained clinical data source; eliminates the single most dangerous failure mode identified in Phase 2.5.
Cons: Requires licensing/maintaining a real clinical drug-interaction database as a dependency, an added integration/cost the pure-LLM approach wouldn't require.
Reasoning: The cost of a missed interaction is categorically higher than any convenience gained from a unified AI approach; this is not a place to optimize for engineering simplicity.
Long-term impact: Establishes the precedent (Model Routing, Section 7) that safety-critical clinical logic is never delegated to purely generative inference anywhere in the system.

ADR-003: Health Graph as Clinical Domain's Internal Model (Not a Separate Bounded Context)

Alternatives: Treat Health Graph as its own top-level domain, separate from Clinical Domain (as your Phase 2.5 brief originally implied).
Pros of chosen approach: Avoids the Graph/Journey/Passport conceptual fragmentation flagged repeatedly across Phases 1.1–2.5; keeps clinical write-authority in exactly one place.
Cons: Makes Clinical Domain the heaviest module in the system (Section 4's overload flag) — a real complexity concentration to manage.
Reasoning: The Graph's entire value proposition depends on it sharing write-authority and consistency guarantees with the rest of clinical content; splitting it into a separate context would reintroduce exactly the cross-domain consistency problems DDD is meant to avoid.
Long-term impact: Clinical Domain will need the most careful internal sub-structuring of any domain in the system, ongoing.

ADR-004: Egypt-Region Data Residency Enforced at Infrastructure Level, Not Application Convention

Alternatives: Trust application-level logic/configuration to route data correctly to Egypt-region storage.
Pros of chosen approach: A misconfiguration or bug can't accidentally violate residency requirements, since the constraint is structural (region-locked infrastructure), not a setting someone could get wrong.
Cons: Real added deployment/infrastructure complexity, especially once multi-region expansion begins (Section 12/13).
Reasoning: Given Egyptian MoH data residency requirements (Phase 1's research) and the severity of a compliance violation, this is not a place to rely on application-level discipline alone.
Long-term impact: Directly shapes the multi-region architecture (Section 12) — each future country needs its own resident storage, not a shared global data layer.

16. Final Architecture Review
    Weaknesses: The Analytics Domain remains under-specified relative to its cross-cutting reach (restated concern from Phase 3) — this document still hasn't given it a full architectural treatment, and it should get one before database design, specifically around how its read access to everything doesn't quietly turn into write-adjacent influence over other domains' behavior.
    Hidden complexity: The Doctor Workspace's "zero context switching" experience (Phase 2.5) implies a genuinely complex client-side state-management architecture (Section 6's "server-authoritative working context") that this document has named but not fully designed — this is real, non-trivial frontend architecture work still ahead in a later phase, not a solved problem.
    Overengineering, honestly assessed: The four-domain AI taxonomy, while product-appropriate (Phase 1.2), risks becoming architecturally over-separated if each domain gets a fully independent service treatment — recommend all four AI domains share the same underlying AI Layer infrastructure (Model Routing, Safety Layer) with only their prompt templates/context-scoping differing, rather than building four independent AI subsystems.
    Underengineering: The Health Graph's actual storage technology choice (Section 9) has been deliberately left conceptual — this is appropriately out of scope for an architecture-only document, but it's worth flagging clearly that this is the single most consequential technology decision still ahead, given how much of the product's differentiation (Phase 1.2) depends on graph query performance actually being good at scale.
    Technical debt, accepted consciously: International Expansion's impact on Trust & Verification (ADR-004's cousin risk, Section 14) is real and not fully solved by the adapter pattern alone — logged again here as a conscious, accepted V1 trade-off, not an oversight.
    Future bottlenecks: Clinical Domain's internal complexity (ADR-003) is the most likely long-term maintainability bottleneck in the system if not actively managed with real internal sub-boundaries and dedicated engineering ownership, restated from Section 14 because it's worth saying twice.
    Missing components, one genuine gap: This document doesn't yet specify a feature-flagging/configuration-rollout mechanism — given how many features here have real risk profiles (AI Copilot behaviors, Emergency Workflow, consent defaults), the ability to gradually roll out, A/B test cautiously, or instantly disable a specific capability platform-wide without a full deployment is a genuine architectural need for a system this sensitive, and it's absent from Sections 1–15. Recommend adding this as an explicit cross-cutting capability before Database Design proceeds.
