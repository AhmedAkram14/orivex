12. Observation Model
Design: A single, generic Observation entity — not a separate table/type per vital sign — with attributes: Observation Type (Blood Pressure / Heart Rate / Temperature / Weight / Height / BMI / Blood Sugar / SpO₂ / Respiratory Rate / future wearable types), Value(s) (some types like BP need two values — systolic/diastolic — modeled as a structured value, not two separate rows), Unit, Recorded Timestamp, Source (Clinical / Patient-self-reported / Device — reusing the same Source attribute pattern from Health Graph Node, Phase 5), and a reference to the owning Health Graph.
Why Observations stay independent from Diagnoses, explicitly: an Observation is a fact (this BP reading was 145/95 at this time); a Diagnosis is a clinical interpretation (this constitutes uncontrolled hypertension). Conflating them would mean every blood pressure reading would need to carry clinical-judgment weight, which is both clinically wrong (a single elevated reading isn't a diagnosis) and would pollute the Graph with false certainty (violating Phase 2.5's Principle 7 on representable uncertainty). Instead, Observations are lightweight, high-volume, confirms/related_to edges pointing toward Condition nodes when a doctor chooses to draw that connection — the connection is a deliberate clinical act, not an automatic one.
Why this also matters for wearables specifically: this design is exactly what makes wearable integration (Phase 5, Section 12) genuinely clean — a wearable device simply produces more Observation entities with Source: Device, at potentially much higher volume/frequency than clinical visits produce, without requiring any new entity type or schema change. This is a strong validation that the Observation-as-independent-entity decision was the right one.

15. Readiness Review
Overloaded entities: Health Graph Node remains, honestly, the entity carrying the most conceptual weight in the whole model — it needs to represent Conditions, Symptoms, Medications, and Lab/Radiology Results all through one typed structure. This is intentional (a unified node type is what makes graph traversal actually work), but it means validation rules and required-field logic will differ meaningfully by Node Type, which is worth flagging now as real implementation complexity ahead, not a modeling flaw to fix at this stage.
Weak relationships worth firming up: The Health Journey ↔ Health Graph Node many-to-many relationship (a node belonging to multiple Journeys) is conceptually necessary but under-specified here regarding how a node's presence in multiple Journeys is prioritized/displayed when they conflict in a UI context — this is more a physical/UI-adjacent concern than a logical-model flaw, but worth carrying forward as a known open question.
Missing entities, found during this pass: A dedicated Referral entity (Phase 2.5's Section 12 "referred out" state) hasn't been given its own logical entity here — it's currently implied as a Health Journey state value only. Given how much weight this concept carries (Phase 2.5 flagged it as a missing concept, Phase 4 didn't fully resolve it either), I'd recommend promoting it to a first-class entity — a Referral record (referring doctor, reason, target specialty/external provider, outcome tracking if known) — rather than leaving it as just a Journey status value. This is a genuine gap worth fixing before Physical Database Design, not after.
Potential normalization problems: Doctor Portfolio Item (Publications, Awards, Memberships from Phase 1.1) is currently modeled as one loosely-typed child entity — in practice these are different enough (a Publication has a DOI/journal reference; an Award has an issuing body/date) that they may deserve to be modeled as distinct sub-entity types rather than one generically-typed table, to avoid a wide, mostly-null-field entity. Worth a closer look in Physical Design specifically.
Future bottlenecks: The AI Suggestion + AI Context volume (flagged already in Phase 5) remains the most significant storage-growth concern in this logical model — every consultation could plausibly generate dozens of suggestion records given the breadth of AI Copilot capabilities (Phase 1/2.5), and this needs deliberate storage-tiering thought at the physical design stage, not an assumption that it'll be "just another table."
Data integrity risks: The clinical-safety constraint in Section 5 (Prescription cannot be Signed while an unacknowledged Warning exists) is the single most important cross-entity business rule in this entire document — it needs to survive into Physical Database Design as an actually-enforced constraint (whether via application-layer transaction logic or a database-level check), not quietly become "a thing the UI is supposed to prevent," which is a much weaker and more fragile guarantee.
