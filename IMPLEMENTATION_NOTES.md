Non-negotiable constraints (see task): real data only, reuse existing APIs/hooks/components, no backend business-rule changes without a written proposal here, explicit confirmation for clinical actions, AI Copilot untouched, i18n EN/AR + RTL preserved, dark-mode tokens only, accessibility preserved/improved, loading/empty/error/success states on everything touched.

## Phase 1 — Data consistency & clinical summary

### Summary

Consolidated the doctor's rating (value + count) onto one shared source across Overview, Patients, Profile and Reports; fixed the stat-tile primitives so a non-numeric value can never render as prose at number size; standardized the frontend's "upcoming appointment" definition and extracted it into a shared helper; and retitled the Patient Chart's chronic-conditions strip to list real condition-type medical-history entries instead of the patient's separate self-reported free-text field.

### Files changed

- **`apps/frontend/src/features/consultation/lib/rating-display.ts`** (new) — `getRatingDisplay(t, { averageRating, reviewCount }, rangeLabel?)`: the one shared value/helper-text formatter for a doctor's rating. Contract: `value` is always a real `"X.X"` figure or `"—"`, never prose. `rangeLabel` (optional) scopes the helper text to a date range (Reports) instead of lifetime.

### Backend proposal — NOT implemented

**Doctor Reports' "Upcoming" tile counts past-dated Confirmed/Rescheduled appointments within the selected report range, unlike every other "upcoming" figure on the frontend.**

`GetDoctorReportsAnalyticsUseCase` (`apps/backend/src/modules/consultation/application/use-cases/get-doctor-reports-analytics/get-doctor-reports-analytics.use-case.ts:104`) computes `upcoming = confirmed + rescheduled + paidUnconfirmedRequested`, where each count comes from `countByStatusForDoctorInRange(doctorId, dateFrom, dateTo)` — i.e. appointments whose `scheduledAt` falls within the *selected report period*, not appointments still ahead of *now*. The use case's own comment documents this as an intentional choice ("plan decision 1": a non-terminal appointment within the period is "on the books, nothing for the doctor to act on," the same practical category as upcoming), not an oversight. By contrast, `GET /doctor/upcoming-work` (used by Overview/Queue) and the Patient Chart's bucketing both require `scheduledAt` to be in the future.

This is exactly the audit's observed symptom (a Sep 8 Confirmed appointment inside the last-30-days window still counting as "Upcoming = 1" in Reports while Overview/Queue/Patients/every chart show 0) — but because the existing code comment frames it as a deliberate design decision from a prior plan rather than a bug, changing its behavior would be a business-rule change, which this phase's constraints say requires a written proposal and discussion, not a unilateral fix. **Not implemented.**

Proposal for a follow-up phase: either (a) rename this tile's underlying concept to something scope-honest like "Open in period" so it never reads as "upcoming" next to pages that mean "future," or (b) add a second, genuinely future-only count if Reports actually needs one. Until decided, Phase 1 instead (i) gave the Reports "Upcoming" tile an explicit `helperText` spelling out what it counts and linking it to the selected range, and (ii) made sure every other page's "upcoming" figure shares one real, future-aware frontend definition (`isUpcomingAppointment`) so they can't drift from each other the way they drifted from Reports.

### The "Verification approved... Reason: Credentials verified" copy fix

Read `notify-applicant-of-verification-decision.handler.ts` in full before touching it, and confirmed the "Reason:" prefix is pure string-template copy, not logic: `VerificationCaseDecidedEvent.reason` is a free-text note an admin can attach to *any* decision (approve/reject/more-info), and the handler used to prefix it with "Reason:" unconditionally whenever present (`` `${base} Reason: ${event.reason}` ``). That reads naturally for a rejection ("...was rejected. Reason: ...") but wrong for an approval with an admin note like "Credentials verified against the medical syndicate registry" -- "Reason: Credentials verified" sounds like a rejection justification, not a positive confirmation.

**Before:** `event.reason ? \`${base} Reason: ${event.reason}\` : base` (same "Reason:" wording regardless of `status`).

**After:** the prefix is now status-aware -- `Rejected` keeps "Reason:" (that framing is correct there), `Approved` uses neutral "Note:" instead, and `MoreInfoNeeded` appends the note with no label at all (its own base sentence already explains what's missing, per the handler's pre-existing comment). No business logic changed -- same event payload, same three statuses, same notification fields; only the copy template. Added a new test (`notifies the applicant of an approval with an admin note, using neutral "Note:" phrasing instead of rejection-style "Reason:"`) covering the exact scenario the audit reported; the two pre-existing approved/rejected tests still pass unmodified.

## Phase 9 — Session & earnings verification

### 1. Session refresh race — root cause and fix

**Confirmed genuine race, fixed frontend-only.**

Read, in order: `features/auth/hooks/use-silent-refresh.ts`, `features/auth/api/session-bootstrap.ts`, `features/auth/api/auth-api.ts`, `shared/auth/token-storage.ts`, `features/auth/providers/session-provider.tsx`, then the backend's `apps/backend/src/modules/authentication/application/use-cases/refresh-session/refresh-session.use-case.ts`, `.../domain/entities/session.entity.ts`, `.../infrastructure/prisma/prisma-session.repository.ts`.

Findings:
- The access token lives in memory only, **per tab** (`shared/auth/token-storage.ts`'s module-level variable — a fresh JS module instance per tab, never shared). The refresh-token credential, by contrast, lives in **one** httpOnly cookie shared by the browser across every tab of the origin — this is the one piece of state two tabs genuinely contend over.
- The backend rotates the refresh token **in place on every use** (`Session.rotate`, `session.entity.ts:88-92`; `refreshTokenHash` is a `@unique` column, `prisma-session.repository.ts:19-22`). One login = one `Session` row (`session.entity.ts:28-30`'s own comment: "rotated in place... never a growing history table"). Presenting an already-rotated-away hash returns "not found" (confirmed by `refresh-session.use-case.test.ts`'s "rejects an unknown refresh token" case) — it does **not** hit the reuse-detection/revoke-all branch, which only fires when a hash that's still on record is found already marked `revokedAt` (a genuinely stolen/reused token, a different scenario from this race).
- `features/auth/api/auth-api.ts` already had a **same-tab** fix in place before this phase: `inFlightRefresh`, a promise-coalescing guard, whose own comment documents an earlier, already-fixed intra-tab instance of this exact race (`useSilentRefresh`'s timer vs. `bootstrapSession`'s realtime-notification-triggered recovery colliding within one tab). That guard is scoped to one JS module instance, i.e. one tab — it does nothing across tabs.
- **No cross-tab coordination existed anywhere** (`BroadcastChannel`, `navigator.locks`, and a `storage` event listener were all grepped for across `src/`, zero matches).
- Mechanism: two tabs' independent `useSilentRefresh` timers (scheduled off each tab's own `REFRESH_MARGIN_MS`-before-expiry deadline, which is very often near-simultaneous since both derive from the same original login) each start a `POST /auth/refresh` request reading the same current cookie value. Without any ordering guarantee, both requests can reach the backend and read the still-matching row before either commits its rewrite; both then write a new hash to the same row's `refreshTokenHash` column (`prisma-session.repository.ts:31-34`'s `upsert` keyed on `id`, not conditioned on the hash it read), so whichever request's write lands last in the database wins — independent of which response's `Set-Cookie` the browser ends up keeping (a second, independent race). Whichever tab's belief doesn't match what's actually persisted fails its *next* refresh with "not found" and drops to unauthenticated in that tab alone — reading to the user as an abrupt sign-out (the audit's report), even though the underlying session was never actually invalid and the *other* tab is unaffected.
- This does **not** trigger the catastrophic "every session revoked" reuse-detection branch under this exact mechanism (that requires a hash to be found *and already revoked*, not merely superseded) — so a full account-wide logout from just two tabs racing is not what the code does today; the `Session` row itself stays valid, only the *losing* tab's own belief goes stale. `Session.rotate`/`revoke` are Sprint 15's standard security posture (rotation + reuse detection) and were **not** touched or weakened.

Fix implemented (frontend-only, does not change what token the backend accepts or how it validates one):
- **`apps/frontend/src/shared/auth/cross-tab-refresh-lock.ts`** (new) — `withCrossTabRefreshLock(run)`. Uses the Web Locks API (`navigator.locks.request('orivex:auth-refresh', run)`) to serialize every `/auth/refresh` call browser-wide, across every tab of the origin, not just within one. When unsupported (Safari < 15.4), it runs `run()` directly — same-tab coalescing via `inFlightRefresh` still applies there; only the cross-tab race can still occur, and only in that older browser.
- **`apps/frontend/src/features/auth/api/auth-api.ts`** — `refreshSession()`'s `inFlightRefresh` promise now wraps the `apiFetch` call in `withCrossTabRefreshLock(...)` instead of calling it directly. Same-tab coalescing (`inFlightRefresh`) is unchanged/kept — the lock adds the missing cross-tab layer on top, it doesn't replace the existing guard.
- Effect: at most one `/auth/refresh` request is ever in flight browser-wide at a time. Every subsequent request (whichever tab it comes from) is guaranteed to observe the true current cookie value (the *previous* request's rotation having already fully committed and had its response's `Set-Cookie` applied before the lock releases), so no tab can ever present a token another tab has already rotated past. This eliminates the race outright rather than mitigating it — no extra retry/backoff logic was needed. The cost is a few redundant-but-cheap sequential rotations if multiple tabs happen to want to refresh at once (each tab still needs its own access-token JWT copy in its own memory, so a fully token-sharing optimization was deliberately not pursued — see "not done" below).
- **`apps/frontend/src/shared/auth/cross-tab-refresh-lock.test.ts`** (new) — 3 unit tests: falls back to running directly when `navigator.locks` is absent; routes through `navigator.locks.request` with the documented lock name when present; and, with a minimal fake `LockManager` that genuinely queues (not just records calls), asserts a second call's callback provably does not start executing until the first's promise has resolved — the actual property that prevents the race, not just "was `request` called."

Second part of the fix — honest "session expired" messaging (also implemented):
- Found that a fully-built, correctly-labeled `/session-expired` page **already existed** (`app/[locale]/(status)/session-expired/page.tsx`, `StatusPage` with `auth.sessionExpired.*` i18n already present in both locales) with a docblock claiming it's "reached when Silent Refresh Architecture's background refresh fails" — but nothing anywhere actually navigated there. `RequireAuth` (`shared/auth/require-auth.tsx`) unconditionally redirected every `unauthenticated` transition to its caller-supplied `redirectTo`, which for every protected layout is `/unauthorized` ("Sign in required" — its own docblock: "For a visitor with no session at all... distinct from Session Expired (had a session, it ended)"). So a genuine mid-session refresh failure and a first-time visitor with no session ever got identical, inaccurate copy — exactly the audit's complaint.
- **`apps/frontend/src/shared/auth/session-expired-flag.ts`** (new) — a tiny in-memory (module-level, per-tab, not persisted) marker: `mark()`/`consume()`. Deliberately not `sessionStorage`/`localStorage` — must not survive a reload or leak across tabs, since a fresh page load with genuinely no session at all must still land on the generic Unauthorized page.
- **`use-silent-refresh.ts`** — the `catch` block now calls `sessionExpiredFlag.mark()` before clearing the token/session (with the cross-tab lock in place, a failure reaching this `catch` now means the refresh genuinely didn't work, not a tab losing a race).
- **`shared/auth/require-auth.tsx`** — on the `unauthenticated` transition, consumes the flag: if set, redirects to `/session-expired?returnTo=...` instead of the caller's `redirectTo`; otherwise unchanged (`/unauthorized`). `returnTo` handling (already-built per Phase 0's finding) is preserved identically either way.
- **`app/[locale]/(status)/session-expired/page.tsx`** — updated to accept and forward `?returnTo=` to `/login`, exactly mirroring `/unauthorized`'s existing pattern (it previously always linked to bare `/login`, silently dropping `returnTo` even though the page's own docblock implied full parity with Unauthorized).

Not done / acknowledged gaps:
- No attempt to make tabs share the *actual* access-token value after one tab's refresh (e.g. broadcasting the new JWT via `BroadcastChannel`) — `shared/auth/token-storage.ts`'s own docblock states the in-memory-only, never-shared-across-tabs storage is a deliberate XSS-surface-reduction decision; broadcasting the token value itself would reopen exactly the attack surface that design closes, so it was ruled out as a security regression, not merely skipped for scope. Each tab still needs to perform its own (now safely serialized, never colliding) refresh call to get its own token.
- `bootstrapSession`'s cold-start refresh failure (page reload with no in-memory token yet) is left mapped to `/unauthorized` as before — deliberately, since that path is genuinely ambiguous (a first-time visitor and a returning visitor whose refresh cookie expired naturally look identical from there) and scoping the fix to `useSilentRefresh`'s unambiguous authenticated→unauthenticated transition (per the task's own framing) avoids guessing at a case the investigation didn't confirm.
- Could not reproduce the two-tab scenario live (no dev server / browser verification per instructions) — the fix is derived from reading the exact rotation/persistence code paths on both sides, not from an observed repro.

### 2. Earnings attribution — root cause and fix

**Confirmed: backend design characteristic ("recognize on payment"), not a bug. Disclosed and linked on the frontend; no backend change proposed or made.**

Read: `apps/backend/src/modules/payment/application/use-cases/initiate-charge/initiate-charge.use-case.ts`, `.../reconcile-stripe-webhook-event.use-case.ts`, `.../get-doctor-earnings-summary.use-case.ts`, `.../get-doctor-earnings-transactions.use-case.ts`, `infrastructure/prisma/prisma-payment-transaction.repository.ts`; `features/payment/hooks/use-doctor-earnings-summary.ts`, `use-doctor-earnings-transactions.ts`, `features/payment/api/types.ts`, `features/payment/components/doctor-earnings-summary.tsx`.

Findings:
- `InitiateChargeUseCase` (`initiate-charge.use-case.ts:94-124`) creates the `PaymentTransaction` and marks it `Succeeded` **the moment the payment gateway authorizes the charge** — which happens right as the appointment transitions `Requested → Confirmed` (`confirmAppointmentUseCase` is called immediately after `markSucceeded()`, line ~127). The transaction is **never revisited** later in the appointment's lifecycle: nothing in `modules/consultation`'s `complete()`/`markNoShow()` transitions, and nothing in the payment module's own event handlers (`auto-refund-on-appointment-cancellation.handler.ts`, `auto-refund-on-appointment-rescheduled.handler.ts` — both cancellation-triggered only), touches a `PaymentTransaction` when an appointment is later completed or goes no-show. So a transaction reads "earned" based purely on payment success, regardless of whether the consultation itself ever actually happened — this precisely explains the audit's "the only earnings transaction shown was for an appointment that stayed Confirmed and reportedly never happened."
- `PrismaPaymentTransactionRepository.findByDoctorId` (`prisma-payment-transaction.repository.ts:53-64`) filters the date-range query by `createdAt` — the **transaction's** creation time (= charge/payment time), not the appointment's `scheduledAt` or any consultation-completion timestamp. `GetDoctorEarningsTransactionsUseCase` and the ranged half of `GetDoctorEarningsSummaryUseCase` (cycles) both pass the UI's `dateFrom`/`dateTo` straight into this same `createdAt` filter. This means the Transactions table and Monthly-breakdown cycles are scoped by **when payment was captured**, not when the appointment/consultation occurred — a real paid, completed consultation whose *charge* happened outside the doctor's currently-selected range (e.g. paid weeks before the visit, or the visit was rescheduled later) would legitimately not appear in that range's view even though the consultation itself is recent. This is the most defensible explanation for "a real completed paid consultation didn't appear as a transaction at all" that the code supports without live DB access — free-of-charge consultations are a separate, unrelated case (`InitiateChargeUseCase` throws and never creates a transaction at all if `pricing.isFree()`, by design; nothing to disclose there beyond what already exists).
- The KPI tiles above (`lifetimeGrossAmount`/`lifetimeNetAmount`/`lifetimeTransactionCount`) are, by contrast, always computed over the doctor's **full, unfiltered** ledger regardless of `dateFrom`/`dateTo` (`get-doctor-earnings-summary.use-case.ts:46-70`, a Phase-0-era fix per its own comment) — so the page combines an always-lifetime KPI row with a range-scoped table/cycles section below it, with the range boundary defined by payment date rather than appointment date. That combination, undisclosed, is exactly the shape of confusion the audit reported.
- This is a legitimate, working "recognize revenue on payment capture" design (a real accounting policy choice, not an oversight) — changing *when* a transaction is recognized, or re-syncing it to appointment-completion, is a business-rule change explicitly out of scope for this phase without a written proposal and discussion. **No such change is proposed here** because nothing found rises to the level of a defect in the recognition logic itself (it behaves consistently and correctly per its own, disclosed rule) — the gap is purely that the UI didn't say so.

## Doctor Schedule redesign (FullCalendar)

- **Library**: FullCalendar 6.1.21 (`@fullcalendar/core|react|daygrid|timegrid|interaction`); no calendar library existed. All five packages pinned to the same 6.x line (a first install mixed 7.x core with 6.x plugins).
- **Files**: new `features/scheduling/components/doctor-schedule-calendar.tsx` + `.css` (tokens only, so dark mode and RTL are inherited); `doctor/schedule/page.tsx` rebuilt around it (the old hand-built week grid/`WeeklyCalendar`/`MonthCalendar` are no longer used by this page); `ScheduleExceptionForm` gained `defaultDate`; new strings in `doctor.schedule` (EN/AR).
- **Data**: unchanged sources. Booked appointments (`useDoctorScheduleAppointments`, padded ±1 day around the visible range) become events; availability, breaks and non-working days come from `resolveDayForDate` + `computeEffectiveWindows` and are drawn as background events. Day headers show each day's effective bookable hours. The slot Agenda and Upcoming Slots tabs keep their existing panels.
- **Timezone**: FullCalendar has no named-timezone support without another plugin, so the calendar runs in UTC and receives Cairo wall-clock time encoded as UTC (same idea as `getCairoNow`). Real instants stay on the appointment objects.
- **Interactions implemented**: prev/next/Today (really move the range), Week/Month/Day switching (Agenda/Upcoming Slots swap the panel), click a time slot (selection bar states whether it is bookable, on a break, or outside hours, with Edit availability / Add time off prefilled with that date), click a month day (opens that day), click or Enter/Space on an appointment (opens it in `/doctor/appointments?highlight=`), vertical scroll (opens on the working day), now-indicator, hover/focus states, overlapping events.
- **Deliberately disabled**: drag and resize of appointments. There is no doctor-side reschedule endpoint, so moving a block would only pretend to persist.
- **Layout**: the summary column (This Week, Next Available Slot) sits beside the calendar from 1536px and below it on smaller screens, so the calendar keeps its width at laptop sizes. Booking rules are now one line under the legend (slot length, buffer, link to Settings) instead of a card. Weekly Availability and Time Off are compact lists side by side. Below `md` the default view is still Day; the week grid scrolls inside its own container.
- **Bugs found and fixed during verification**: an infinite render loop (fresh `initialDate` each render re-firing `datesSet`); navigation controls shown before the calendar existed; tab buttons whose `aria-controls` pointed at a missing panel (axe); appointment text rendering white on pale blocks; the grid opening at 1 AM.
- **Verification**: typecheck and lint clean; `doctor/schedule/page.test.tsx` 15/15 (13 existing + navigation and event tests); browser e2e `doctor-schedule-calendar.spec.ts` (grid and bands, navigation, tab switching, month click, slot selection, 390px no sideways scroll) and the responsive/axe spec: 17/17. Screenshots at 1280px and 390px reviewed against the reference.
- **Not done / caveats**: jsdom cannot lay out FullCalendar, so unit tests assert labels and behavior while real visibility is covered by the browser spec; Arabic/RTL and dark mode of the calendar were not visually reviewed (styles use tokens and `direction` is set from the locale); `booking-flow.test.tsx` "inline payment step" fails on the committed code independently of this work.
